# Project Instructions

## Architecture

Use lightweight, feature-oriented hexagonal architecture adapted to Expo/React Native. This layout describes responsibilities, not a file inventory. Create directories only when needed; update this document only when architectural boundaries change.

```text
.rnstorybook/                # On-device Storybook configuration and shared preview annotations
src/
├── app/                     # Expo Router routes, layouts and application providers
├── api/
│   └── generated/           # Orval-generated HTTP functions and API types; never edit manually
├── components/              # Shared presentational UI and colocated stories
├── hooks/                   # Shared UI and platform hooks
├── constants/               # Shared theme tokens and application constants
└── features/
    └── <feature>/
        ├── domain/          # Business types and pure business rules
        ├── application/     # Use cases and the ports they require
        ├── adapters/        # API/native adapters and DTO-to-domain mapping
        └── ui/              # Feature presentation, orchestration and colocated stories
assets/                      # Images, fonts and other bundled assets
plugins/                     # Expo config plugins for native build configuration
android/, ios/               # Native projects generated by Expo prebuild
tests/                       # Node-based Vitest unit and focused integration tests
```

Dependency direction (arrows mean imports):

```text
app → features/ui → application → domain
app → adapters → application/domain
adapters → api/generated or native APIs
```

- Keep routes thin: compose feature UI and wire adapters to application ports at the application boundary. Keep reusable components, hooks, constants and stories outside `src/app/`.
- Keep domain and application independent of React, React Native, Expo and generated API types. Adapters implement application ports; UI receives dependencies rather than importing concrete adapters.
- Shared presentational components do not depend on features or fetch data. Use `.native.tsx`, `.ios.tsx`, `.android.tsx` or `.web.tsx` variants only when platform behavior differs.

## Orval

Generates typed fetch functions and API types in `src/api/generated/` from the backend's OpenAPI endpoint. Set `OPENAPI_URL` and run `bun run api:sync`; reuse the generated client and never edit it manually. Set `EXPO_PUBLIC_API_URL` to an API host reachable from the device.

## Storybook

On-device UI development and documentation workshop. Keep `*.stories.tsx` next to components under `src/`, with fixed data and no live backend. Run `bun run storybook` with a native development build; configuration lives in `.rnstorybook/`.

Every component creation, update or deletion must include the corresponding story creation, update or deletion.

Consult [React Native Storybook documentation on Context7](https://context7.com/storybookjs/react-native) (`/storybookjs/react-native`) for well-structured, testable stories. Use typed CSF (`satisfies Meta`, `StoryObj` from `@storybook/react-native`) and cover all applicable variants and states through `args` and on-device controls. Keep interactions reproducible without assuming browser-only testing APIs.
