# Project Instructions

## Introduction

This project is an Expo/React Native application boilerplate.

## Architecture

Use lightweight, feature-oriented hexagonal architecture adapted to Expo/React Native. This layout describes responsibilities, not a file inventory. Create directories only when needed; update this document only when architectural boundaries change.

```text
.rnstorybook/                # On-device Storybook configuration and shared preview annotations
src/
├── app/                     # Expo Router routes, layouts and application providers
├── api/
│   └── generated/           # Orval-generated HTTP functions and API types; never edit manually
├── components/              # Shared presentational UI and colocated stories
├── hooks/                   # Shared UI and platform hooks
├── constants/               # Shared theme tokens and application constants
└── features/
    └── <feature>/
        ├── domain/          # Business types and pure business rules
        ├── application/     # Use cases and the ports they require
        ├── adapters/        # API/native adapters and DTO-to-domain mapping
        └── ui/              # Feature presentation, orchestration and colocated stories
assets/                      # Images, fonts and other bundled assets
plugins/                     # Expo config plugins for native build configuration
android/, ios/               # Native projects generated by Expo prebuild
tests/                       # Node-based Vitest unit and focused integration tests
```

## Backward Compatibility

- When presenting an implementation plan, flag any changes that cannot preserve backward compatibility.
- Always preserve backend backward compatibility by default: APIs, persisted data, and database migrations must remain compatible with older supported clients.
- Prefer additive changes over multiple API versions. When renaming a field, keep the old field and accept legacy inputs, with one source of truth.
- Database migrations must also support the previous backend version.
- Mark deprecated elements using exactly: `// deprecated on YYYY-MM-DD: <replacement and compatibility reason>`.
- Never remove legacy behavior without explicit approval.
- If backward compatibility is impossible for any reason, explain the breaking change and its impact to the user, and obtain explicit approval **before implementation**.

## Orval

Generates API functions and types in `src/api/generated/` from the backend's OpenAPI endpoint. Set `OPENAPI_URL` and run `bun run api:sync` to sync client with OpenAPI specs when needed; reuse the generated client and never edit it manually.

## Storybook

Create and maintain colocated stories for every shared presentational component in `src/components/`.
Exclude purely technical components such as wrappers, providers, and transition primitives; demonstrate them through the UI components that consume them instead.

Do not create stories for components in `src/features/<feature>/ui/` by default; add them only when explicitly requested.

- Provide a fully customizable playground through `args` and Controls for all public inputs: content, variants, sizes, states, and behavior.
- Configure `argTypes` with appropriate controls and all supported options, including every variant and size.
- Forward `args` to the component; do not hardcode values that prevent customization. Use editable `args` for inputs that cannot be represented by Controls.
- Use realistic, deterministic data without a live backend.
- Cover distinct, useful states—not every possible prop combination.
- Keep interactions functional; use React Native-compatible callback spies and meaningful interaction checks.
- Colocate `*.stories.tsx`, use typed CSF (`satisfies Meta`, `StoryObj`), and keep stories aligned with component changes and removals.

Consult [React Native Storybook documentation on Context7](https://context7.com/storybookjs/react-native) (`/storybookjs/react-native`).
